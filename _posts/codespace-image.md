# Codespaces用のDockerイメージ作成時のヒント

## Codespaces用のイメージの特殊性

Github Codespacesは用意されているイメージのファイル構成を使用しBashを起動する事により、ターミナル環境を提供します。
運用されるユーザはデフォルトでrootユーザが使用されます。
イメージをコンテナとして起動したのちに、対応するリポジトリのイメージを"/"ディレクトリにコピーを作成し、そのディレクトリを作業ディレクトして設定して、Bashを起動します。

### ユーザごとに環境を設定するソフトウェアのインストールに注意

NodeJSやAnaconda3などのアプリケーションはユーザごとにインストールが標準では行われるため、使用するユーザはデフォルトではrootになることを注意してください。
ソフトウェアによってはrootでの作業を制限しイェイるものもあ知ますので、注意が必要です、

インストールをDocker buildなどで行う場合はインストール先を/optなどに指定するなどの工夫が必要です。

### DockerのExpose設定はCodespacesでは必要ない。

Codespacesではターミナル環境でポートを公開するソフトウェアが実行された場合、VSCODEなどと連携してローカルのPCからアクセスできるようポートマッピングが動的に行われます。
VSCODE上から手動でのポートマッピングも設定できるので、イメージを専用に使用する場合には設定しておく必要はありません。

### 用意したイメージをGithub Actionなどと共有する場合の注意

#### 環境変数の設定の方法に注意

DockerのイメージをGithub Actionなどで流用する場合には”常にBash経由でコマンドが実行されるわけではない”ということを留意する必要があります。
パッケージのインストーラはインストール時のユーザのシェル環境設定ファイルにパッケージ用の環境変数を設定するものも多く見受けられます。
この場合、シェル経由でのコマンド起動であれば、その環境変数も反映されますが、Docker Execでのコマンドの直接起動などでは、その定義が反映されません。
コマンド実行に必要な環境変数はイメージ内のENV 設定で必ず定義しておきましょう。

#### 起動コマンドが異なることに注意

作業用コンテナとして流用する場合にはコンテナ内の様々なコマンドが直接起動されることを考慮する必要があります。
Systemdを前提としてイメージを作成して打てもINITが実行されない場合がありますので、動作確認の確認は必要です。

## DockerイメージとPodmanイメージの違いについて

Github Codesopacesで使用する場合、両者のイメージに違いはありません。

ただし、Redhatのリポジトリに直接接続する場合には認証およびアクセス権の問題で、Codespaces上で問題にあなることが多いです。

イメージ作成に関してはRedhatのルールに従ってください。
